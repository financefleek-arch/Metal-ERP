Unit handling. Every item already carries rate_mode (piece | kg) and uom; secondary_uom exists for items sold two ways. The line:
  • on pick → unit = item's uom, defaulted, never the full 16-entry list
  • one unit → shown as a badge on the Qty label, no dropdown; Rate label reads ₹/<unit>
  • two units (uom + secondary_uom) → dropdown of exactly those two
  • new typed item → a per piece / per kg choice in the "new item" strip sets the created item's rate_mode + a default uom (nos / kg)
  • changing the unit does not convert qty or rate — the stored factor (weight_per_piece/conversion_factor) is not wired in this pass; user types qty + rate for the chosen unit
Backend: no migration. One field (secondary_uom) added to the /items + /items/resolve response so the editor can narrow the list.
Discount toggle — the one trade-off: the backend line stores an absolute discount only. A line entered as "10 %" is sent as the computed ₹ amount, so after finalize + reload it shows as "₹236 (₹)". The invoice is frozen by then and ₹ is the source of truth, so this is acceptable — noted here so it's a decision, not a surprise. (Persisting the % would need a new discount_pct column — separate, later, only if you want the editor to remember it.)
Not in this change: desktop layout, the search wiring, the totals rail, tax.py, the PDF. Mobile LineRow markup + the "now" guards above. The "later" rows need a data signal or a small backend touch and are tracked separately.
