The catalogue teaches itself

The shop never maintains an item list. Inward bills seed a first-cut catalogue as they're uploaded. Billing refines it — the biller types the terse shorthand they always have (hawkins 5, dhara kettly 10cup, ST storage box 12x18) and the system resolves it to a product + size, learns the mapping, and generates the clean printed name. Two learning loops over a three-level model; a rules-first parser; aliases that stick on the second use.

What this tells the model:
  • A line = one product, one size, one rate. The bartan inwards pool weight across sizes on one row; the target bill puts one row per size. We emit one row per size (leaf) and print the product name as a sub-header when consecutive rows share it.
  • Rate mode varies by product: storage boxes / dhegchi / kadai → per kg. Hawkins / Mintage / Dhara → per piece. This lives on the leaf (default from its group).
  • Brand is the section a customer navigates by — "Hawkins 5 litre", "Mintage 3499". So brand = category. A no-brand stainless item's category is a material tag (ST, GS).
  • Names are terse Hinglish shorthand with no delimiters — C.B.KADAI 12X18, SINI ShivShakti 92.380×305, Dhara Kettly 10cup 6PC→425. A rules-first parser splits brand / product / size / qty / rate / mode; the messy residue is flagged.

Who owns what
  • Category — just a name, tenant-scoped. product_group.category_id; a loose group-less item also carries category_id. Seeded on register with a starter set; the shop renames/replaces (a bartan shop turns them into brands).
  • Product group — hsn_code, item_type, and a default rate_mode (piece | kg). Metal-bar shops also set metal/shape/grade here; utensils leave them blank.
  • Item (leaf) — size_text (free: 12X18, 10cup, 7.5Ltr, No.14), size_pos orders them; rate_mode (from group, overridable — a family can mix); weight_per_piece when rate_mode=kg; own default_rate / price_min/max / last_rate / last_purchase_rate; usage counts. The article/model no. (3499) rides in the name for now — sku stays dormant.

The shared parser — parse_product_line(text)

Rules first. A size grammar + a tenant brand list + normalize.py handle the ~80% that's structured. Ambiguous lines are flagged for review (or, opt-in, one batched LLM call per inward bill — reuses the inward module's llm service, off by default). Nothing here calls an LLM on the billing type-ahead.

parse_product_line → { brand, product, size, size_kind, rate_mode, qty, rate, confidence }
Raw line→ parsedHow
ST STORAGE BOX 12X18 … 273.685 KGS @ 182/KG brand ST · product Storage Box · size 12X18 (NxN) · mode kg · rate 182 ST prefix → brand; "per KGS" col → kg; \d+X\d+ → size
Dhara Kettly 10cup 6PC → 425 brand Dhara Kettle · size 10cup (cup) · mode pc · qty 6 · rate 425 "Kettly"→"Kettle" (synonym); \d+cup → size; \d+PC → piece
Mintage 3499 5Ltr 1PC → 1820 brand Mintage · model 3499 (→ name) · size 5Ltr (litre) · mode pc · rate 1820 brand list; \d+(\.\d+)?\s?l(tr)? → size; leading number after brand = model → kept in the generated name
SS 16→16 1 × 2500 brand SS · size 16 · mode pc · qty 1 · rate 2500 · conf 0.55 bare number in size slot; 1 × integer qty → piece. Low confidence → row flagged.
SINI ShivShakti 92.380 × 305 brand SINI · product ShivShakti? · mode kg · conf 0.4 — flag decimal qty → kg; "ShivShakti" — model or product, unclear → reviewer decides / LLM residue
BK 4° 13.600 × 400 product BK · size 4 · mode kg · conf 0.45 — flag decimal qty → kg; "BK" not in brand list → flag, name = raw text until human tidies
Size grammar (first match wins): \d+\s?cup · \d+(\.\d+)?\s?l(tr|itre)? · \d+\s?[xX]\s?\d+ (NxN inches) · no\.?\s?\d+ · \d+\s?(mm|g|gauge|G)\b · bare \d+ when a size slot is expected and nothing else claimed it.
Rate-mode heuristic: a "per KGS/KG" column → kg · \d+\s?PC or \d+\s?NUG → piece · a decimal quantity → kg · an integer quantity with × → piece · else inherit the group's default.
Brand list is a per-tenant table (brand), seeded from what inward bills reveal, editable.

Loop 1 — inward bills seed the catalogue

Runs inside the inward-approve transaction (lands after the inward module ships). Every approved line teaches the catalogue.

learn_from_inward(bill)

app/services/catalogue/learn_from_inward.py · called from inward approve
1parse_product_line each line → brand / product / size(s) / rate_mode / rate
2resolve_group(normalize("ST Storage Box")) → exact product_group.name_normalized → group alias → trigram. No hit → create the group: category from the brand/prefix (create the category too if new), rate_mode from the line, hsn_code from the line.
3For each size token → resolve-or-create the leaf: size_text, size_pos (from the parser's size_sort), rate_mode, sku if a per-size model number was on the line, last_purchase_rate (₹/kg — same for all sizes on the line).
4Pooled-weight line (one row, several sizes, one total weight): the inward line links to the group (inward_bill_line.group_id), the size×pieces breakdown goes to inward_line_size rows, the pooled weight/value stays group-level. A [split by weight] action distributes it once weight_per_piece is entered for those sizes.
5Write the line's wording as a group alias (+ per-leaf alias where the size was explicit), source=auto_from_purchase — never auto-retired.
Everything status = unconfirmed. After ~5–10 bills the catalogue is mostly there — nobody typed it. Low-confidence parses → item named after the raw text + flagged. Dry-run mode parses a bill and shows what it would create without writing — use it to check parser quality on real PDFs before switching learning on.

The shop grew its catalogue by billing. The Items "Unconfirmed" filter is the (optional) review queue.
Alias trust — a billing shorthand becomes a stored alias on the 1st use (marked source=learned, last_used_at), so bill #2 is instant. A nightly sweep retires learned aliases unused for 90 days, so a one-off typo like hawkins 55 self-cleans. Inward-derived aliases (source=auto_from_purchase) came off a real document and never auto-retire. Every learned alias is also deletable from the review queue.
