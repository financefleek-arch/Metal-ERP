F3b — Party statement → WhatsApp

One tap on a party → a PDF of the account ledger for a chosen period (opening balance → entries → closing) → send it on WhatsApp (or just download). Reuses party_ledger() for the rows and the existing invoice-send WhatsApp path for delivery.

PLAN — nothing built. Scope: docs/SCOPE-F3-F4-collections-and-tally-handoff.md §A.2. New services/statements.py::render_party_statement_pdf(), template templates/statement_v1.html, GET /api/parties/{id}/statement.pdf?period=&from=&to= and POST /api/parties/{id}/statement/whatsapp. New Meta template account_statement (party_name, total_due) — submit now, approval takes days. Depends on F3a for the Overdue chip + per-row "Send statement" entry point. No migration — whatsapp_message already has a nullable party_id FK (separate from invoice_id); a statement row is party_id set / invoice_id null.
Decided 2026-09-09. Period picker = preset dropdown: This month (default) / Last month / This FY (Apr–Mar, hard-wired) / Last 90 days / Custom range. Statement opens with a synthetic "Opening balance as on <start>" row (running balance rolled forward), then the window's entries, then the closing balance. Content = full ledger for the window, not open-bills-only. Reversed payments inside the window stay in — struck-through with a "reversed" note — never omitted (keeps the history + arithmetic honest). Empty window (no entries) → the Send button is disabled with "Nothing happened this period" — no point sending opening = closing. Closing line wording = "Total due ₹X". File name = <Party slug> statement <YYYY-MM-DD>.pdf (today's date, matching download_name() for invoices — not a period token). Custom range fields render inline and work identically on phone + tablet. No migration — whatsapp_message.party_id already exists. Entry points: Party Account tab (Download + Send) and the F3a Collections per-row "Send statement" on overdue parties. Bulk multi-select send stays in F3c.

4 · The statement PDF

New template templates/statement_v1.html, same Jinja env as the invoice PDF (money / kg / uom filters, Indian digit grouping). Rows from party_ledger() sliced to the window. Regenerated on demand — no persisted pdf_path. File name via the existing download_name() helper: "<Party slug> statement <YYYY-MM-DD>.pdf" where the date is today (generation date), matching how invoice PDFs are named — not a period token.

Opening-balance row. The first row is always a synthetic "Opening balance as on <start>" — the running balance carried forward from everything before the window (the party's own opening_balance + every earlier invoice − every earlier payment). Then the window's entries. Then closing. So a "This month" statement starting 01 Sep shows the balance as it stood on 01 Sep, not the all-time opening balance.

5 · Endpoints

Download

GET /api/parties/{id}/statement.pdf?period=this_month
period ∈ this_month | last_month | this_fy | last_90 | custom; custom requires from=&to= (ISO dates). this_fy = 1 Apr of the current Indian FY → today (hard-wired April, no tenant setting). Server resolves the window, computes the carried-forward opening balance, slices the ledger, renders, streams with a friendly Content-Disposition name.

Send

POST /api/parties/{id}/statement/whatsapp
Body {period, from?, to?, to_phone?}. Renders (same resolver) + _send_template_message() with account_statement (party_name, total_due). 422 if the window is empty. Writes a whatsapp_message row (party_id set, invoice_id null) and returns it so the dialog can show "sent".
