Items — create, read, update, delete

Same shell as Parties: list rail + inline detail pane, create-in-place, autosave, an ⋯ menu with archive-vs-delete. Items are not standard SKUs — a name is metal · shape · grade · size ("SS 304 Patta 4in 2mm"), so the catalogue accretes from what gets billed and purchased, resolved by fuzzy search, not an LLM. Price carries an optimum band that warns (never blocks) on an out-of-range invoice rate.

Resolution — normalize + trigram, no LLM

Metal item names are compositional, not prose. The variation is token order, abbreviations and unit spelling — exactly what a synonym map + pg_trgm handles. An LLM adds latency, cost and non-determinism to a mid-sale type-ahead for no gain when the fallback is "pick from 5 rows or type the name once".

The shared ladder (services/item_resolution.py, used by invoice-finalize accretion and inward line-matching):
  • normalize(text) — lowercase → collapse whitespace → strip punctuation → apply the tenant synonym map (stainless→ss, alu→aluminium, thk→thick, mm.→mm) → canonicalise dimensions (40 x 40/40*40/40X40 → 40x40; 2"/2 inch/2in → 2in; strip thousands separators) → keep token order.
  • Step 1 — exact name_normalized match (tenant-scoped). Step 2 — item_alias match. Step 3 — pg_trgm similarity ≥ 0.55 over name + aliases, HSN as a boost/tie-break.
  • No hit → on the invoice the free-typed name stays as line text and the item row is created at finalize (source=auto_from_invoice); on an inward bill it's a staged new item created on Approve (source=auto_from_purchase). Both land status=unconfirmed.
  • LLM disambiguation: an inward-only, batched, opt-in step for the ambiguous residue — shipped as a stub, off by default. The invoice type-ahead never calls it.

The three create paths
  • Items + New → POST /api/items, source=manual, status=unconfirmed. Explicit Create button (no row to autosave into yet). Normalized-key collision → 409 with a link to the existing item.
  • Invoice, free-typed name, no match → stays as line text; the item is created inside the finalize transaction, source=auto_from_invoice, uom + last_rate from the line.
  • Inward bill line, no match → staged; created on Approve, source=auto_from_purchase, last_purchase_rate from the line, HSN if the code is in the reference list.
All three appear in the rail under Unconfirmed until someone opens them and hits Confirm (or Merge).

Dedupe, Confirm, Merge, Archive, Delete

Curation actions (the ⋯ menu + review filters)
  • Confirm — unconfirmed → confirmed. The rail’s Unconfirmed filter is the review queue; a confirmed item drops out of it.
  • Merge into… — pick a target item; sets merged_into_id, moves the loser’s name to an item_alias of the winner (so the next inward/invoice line with that wording matches at step 2), repoints existing invoice_line.item_id. The merged row is hidden but kept.
  • Archive — status=archived: out of the type-ahead and default list, kept for old invoices. Reversible.
  • Delete — hard, only when times_billed = 0 and no invoice_line / inward_bill_line references it. Otherwise blocked with the count → Archive instead.
Collision on create / rename
  • Same name_normalized for the tenant → 409: “looks like an existing item: SS 304 Patta 4in 2mm” with a link.
  • A near-match (trigram ≥ 0.8, not exact) on the + New form → inline soft banner, Create still allowed (it might genuinely be a different size).
  • The unique constraint uq_item_tenant_normname already exists — this is enforced, not advisory.
