Metal ERP · Visual review · Items · Bulk operations

Fix a hundred items in one move

A shop owner just imported 2,094 items from Tally. Half have no unit, a whole brand needs a 5% discount, a mis-spelled category needs merging away. Doing that one item at a time is the current reality. This plan adds select → change one thing → preview → apply to the existing Items screen — no new page, no jargon, nothing a counter-hand can't run.

Reuses two-pane Items shell List rows gain a checkbox Bulk-edit sheet Preview-before-apply PATCH /api/items/bulk POST /api/items/bulk-delete

00 Where this sits today

Items is a two-pane screen (web/src/pages/ItemsPage.tsx): a left rail with a Tree view and a Flat list + search + filter chips (All / BULK / MRP / Unconfirmed / No HSN / Price review / Archived), and a right pane that edits one item with autosave. Every edit is a single PATCH /api/items/<id>. Delete is per-item and blocked when the item is on any document. There is no multi-select anywhere.

Design constraint carried from ui-plan-guardrails: this is Level 1 — the 1B two-pane pattern. Bulk ops must live inside that shell (the Flat list), not spawn a spreadsheet. A layman drives it: no formula bar, no column config, no "apply to filtered set" surprises. You touch only the rows you can see ticked.

01 The core interaction

Four states on the Flat list. The Tree view stays selection-free (it's for browsing hierarchy); bulk work happens in Flat where rows are uniform.

  1. Select. A checkbox appears on hover / is always visible on touch. Tick rows, or tick the header box to select every row currently loaded by the search+filter. Shift+click ticks a range.
  2. Act. The moment one row is ticked, a teal selection bar replaces the list header: “12 selected · Edit fields · Change category · Delete · Clear”.
  3. Preview. Whatever you choose opens a sheet in the right pane. You set one or a few fields; a live table shows exactly which of the 12 items change and which are skipped, and why.
  4. Apply. One button. One request. A toast: “Updated 9 items · 3 unchanged”. Selection clears. The list refetches.

02 Bulk edit fields — the sheet

Opens in the right pane (replaces the single-item form while a selection is live). Each field has an enable toggle: off means “leave every item's value alone”. Only enabled fields are sent. This is the whole trick that makes it layman-safe — you can't accidentally blank 12 fields because you only see one form.

03 Bulk category / group — a guided move

Category and group deserve their own flow because they're a hierarchy, not a value, and because the other session's classifier (item-categorization-plan) makes moves here teach a rule. Same select → preview → apply spine, different picker.

What the user picks

  • Category — dropdown of the tenant's item_category list, or “＋ new category”.
  • Group — dropdown filtered to that category's groups, or “leave as-is” / “remove from group”.
  • A checkbox: “Also apply this group's HSN & unit where the item has none” — reuses _apply_group_inheritance, off by default so nothing silently changes.

What happens under the hood

  • Each item: PATCH with group_id / category_id — the same path as the single form.
  • For every item that was unconfirmed, the existing learn_from_recategorize hook fires → a tenant classify rule is written. Bulk recategorizing 40 kadais teaches the classifier “kadai → Cookware / Kadai” in one move.
  • Preview shows: N items move · M rules will be learned · K get inherited HSN/UOM.
Coordination with the categorization session: that session already plans a “recategorize control … mostly there” in the Items UI and a tools/reclassify_items.py CLI for the 2,094-item first pass. This plan does not duplicate the CLI — it gives the owner an in-app way to fix the residue the classifier leaves in Other / Uncategorised, item by item or forty at a time, and each fix feeds the same learning loop. Build order: categorization lands first (it seeds the taxonomy + rules table), then this slice wires bulk into it.

04 Bulk delete — the careful one

Delete is destructive and the current per-item rule already blocks items that are on documents. Bulk delete keeps that rule and makes the split visible before anything happens.

Rules

  • Server re-checks times_billed + document_count for every id — the preview is advisory, the API is the guard (same 409 logic as delete_item).
  • Two explicit buttons: Delete the deletable, Archive the rest. Never one button that does both silently.
  • No “type DELETE to confirm” — the count-in-the-button + the deletable/blocked split is the friction. A layman reads “Delete the 8”, not a ritual.
  • Merged/archived items are filtered out of selection already (list query excludes them).

05 API — two endpoints, both preview-capable

Both accept ?dry_run=true and return the same per-item outcome list the UI renders as the preview. No new service layer — they loop the existing single-item logic inside one transaction.

EndpointBodyReturnsStatus
PATCH /api/items/bulk { ids: [...], fields: { uom?, default_discount_pct?, group_id?, ... } } per id: changed | skipped(reason) | error(msg); plus learned_rule_ids new
POST /api/items/bulk-delete { ids: [...], on_blocked: "skip" | "archive" } per id: deleted | archived | blocked(n_docs) new

Reused as-is

  • update_item's body loop, name-clash guard, _apply_group_inheritance, hsn_gst_rate fill, learn_from_recategorize.
  • delete_item's document_count + times_billed 409 rule.
  • confirm_item for the batched status change.
  • Tenant scoping via _owned per id — an id from another tenant → that id reports error, the rest proceed.

New, small

  • Pydantic ItemBulkUpdate / ItemBulkDelete in schemas_item.py.
  • A BulkOutcome row model (id, name, result, detail).
  • Guard: max 500 ids/request (the SETHIA import is 2,094 — the UI pages, or the CLI handles the whole-catalogue pass).
  • One transaction; partial success is normal and reported, not rolled back. A true error (constraint) rolls back only that item.

07 What we are NOT building

Inline grid editing

No click-a-cell-and-type on the list. That's the 2B dense editor and it's a different, later slice. Bulk = one value to many rows, not a spreadsheet.

Saved selections / segments

Selection is ephemeral — it clears on apply and on navigation. Filters already do the “find this set” job.

Undo

No transactional undo. Mitigations: preview before apply, delete is archive-first for referenced items, and every field change is re-editable. Notes “replace” is the only lossy op — it warns.

Bulk create

Out of scope. Creation comes from imports (Tally / inward) and the single New form.

New taxonomy / classifier

Owned by item-categorization-plan. This slice consumes it.

Cross-tenant / admin bulk

Everything is tenant-scoped through _owned. No superuser path.
