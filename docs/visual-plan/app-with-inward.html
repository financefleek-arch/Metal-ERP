It adds no columns to the shared masters and touches no M1 screen — it reads party / item / hsn_code and writes back through the same catalogue-accretion path a sale already uses.

What the module changes in the rest of the app

Untouched

  • Every M1 screen — Dashboard, Sales, Items, Parties, Firm — renders identically whether the flag is on or off.
  • The shared tables. party, item, item_alias, hsn_code get no new columns for this module (two purchase-rate fields on item were already in the dormant schema).
  • Auth, tenant model, role gate, deploy pipeline — one container, one DB, one migration chain.

Touched, lightly

  • Shell nav — one conditional item at the end of the bar.
  • Items page — purchase-created items land here as unconfirmed alongside sale-created ones; the existing "Unconfirmed" chip already covers them. A new source = auto_from_purchase value is the only tell.
  • Parties page — a supplier auto-created from a bill shows up like any other; a matched customer may be promoted customer → both.
  • Shared services — domain/normalize.py and the item-resolution ladder are built once and called by both sales finalize and inward line-matching.
