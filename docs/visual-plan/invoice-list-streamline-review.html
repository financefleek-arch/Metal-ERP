Invoice list — streamline before adding WhatsApp tracking

BUILT 2026-09-08 (uncommitted). Decisions locked: WhatsApp column = glyph + word (§2); PDF stays a visible row button, everything else in the ⋯ menu; payment = dot + word in the meta line (§2); "FINAL" dropped — only Draft / Cancelled get a coloured word. §3 (glyph-only) and the "keep the pill" variants were not taken.

1 · Where we are today

Two stacked status badges (FINAL over UNPAID) + three-to-four always-visible action buttons per row. Dense, repetitive, and there is nowhere left to put a WhatsApp indicator without a third badge stack.

Problems. (1) FINAL repeats on every numbered row — it is implied by having a number. (2) Payment state is the useful signal but it is the second, smaller badge. (3) Four buttons wide; "Duplicate" and "Delete" are rare. (4) No room for WhatsApp / email / print status without a third stacked badge.

2 · Streamlined row (proposed)

Number + party lead. State becomes one quiet word, not a badge. Payment becomes a coloured dot + word in the amount cell (where money belongs). Primary action is the whole row (opens the invoice); everything else collapses into one ⋯ menu. A single WhatsApp column shows send status at a glance.

What changed. · FINAL badge → plain word "Final" in the meta line (grey). · Payment → colour dot + word, in the meta line, with the ₹ due amount when partial. · Date moves under the party (it is reference info, not a column worth 84px). · Actions → one ⋯ menu. The row itself opens the invoice; that covers 90% of clicks. · New WhatsApp column: one glyph + word, colour-coded, tooltip carries recipient + timestamp + failure reason. · Grid goes from 6 columns to 5 and is visually quieter despite carrying more information.

5 · Full history — on the invoice detail, not the list

The list shows the latest status. Every send attempt + its timeline lives on the invoice detail page, in a small card below the header, with a Resend button. The list column and this card read the same GET /api/invoices/{id}/whatsapp.

Backend needed. One read route: GET /api/invoices/{id}/whatsapp → [{to_phone, status, sent_at, delivered_at, read_at, error, wa_message_id}] (the whatsapp_message rows already exist and are already updated by the webhook fan-in). List serializer also gains a single whatsapp_status string = latest row's status, so the list column needs no per-row fetch. Poll while any row is pending/sent.

  • Does "Final" need to appear at all on a numbered row, or is the number enough and we only label Draft / Cancelled?
