Stacks of sizes: one barcode + a size number

Loose finished vessels can’t each carry a barcode. So the stack gets one label encoding a group code. The barcode points at the size family, not a SKU. Sizes are a stable ordered sequence (smallest…largest = 1…5). Scan the stack → system knows the family → operator types the size number → line added at that size’s price.

Prices, sizes, HSN all live in the backend, so a price change or a 6th size needs no reprint.

Clean single-SKU case — unchanged
Boxed goods (Prestige tope) or items with a maker EAN-13 → barcode maps straight to one item. Scan = add 1 at MRP−discount, no number prompt. Scan-scan-scan.
Schema — barcode maps to a GROUP or an ITEM
product_group(id, name, category, hsn_sac, uom, item_type, group_code UNIQUE, default_size_pos NULL)
item(id, group_id, size_pos INT, size_label TEXT, name, mrp, last_rate, item_code, stock_qty, …)   UNIQUE(group_id, size_pos)
barcode_alias(id, code, target_type ENUM('ITEM','GROUP'), target_id, source ENUM('OWN','MANUFACTURER','VENDOR'))
label_batch(id, kind[STACK|SKU|LOT], target_ids[], layout, created_by)  — reprints
stock_lot(id, item_id, lot_code UNIQUE, net_kg, weighment_id, status)  — BULK, Stage 4
size_pos is the contract between label and operator — once No.3 = average, it stays 3 forever. Insert a size → it becomes 6, or renumber deliberately and reprint.
Honest limit: the barcode can’t see which vessel was pulled, so one keyed digit is inherent. Scan + one digit, range-checked, one label per stack. If that’s still too slow in a rush, the fallback is a size-button keypad for top groups on the billing screen — not per-piece barcodes.
