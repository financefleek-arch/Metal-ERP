Pushing finished invoices back into Tally

Tally stays the accounting book. On finalize, our platform builds a Tally Sales voucher as XML and POSTs it to the shop’s Tally over LAN via the connector agent. One-way push. Tally has no REST / webhooks — it’s XML-over-HTTP IMPORT DATA into the built-in server on :9000.

Learn the exact dialect by exporting one hand-made voucher and mirroring it. Errors return <LINEERROR> — a bad ledger name fails the whole voucher.

Idempotent: voucher number = our invoice number + a UDF key — a retry never double-posts. Finalize is not blocked on Tally; it queues.
What Tally exposes (all of it)
XML / HTTP :9000 — EXPORT (read) + IMPORT DATA (write). The main channel.
ODBC :9000 — read-only SELECT from Tally “tables”.
TDL — Tally’s extension language; custom reports / export formats / an in-Tally “send” button.
Tally.NET sync — Tally-to-Tally only.
No REST/JSON, no OAuth, no webhooks. New-voucher awareness = poll the day book.
Plan around
Tally must be open with the right company loaded — health-check, clear “unreachable” state, queue don’t block.
LAN-only — cloud can’t reach 192.168.x.x:9000, hence the connector agent.
XML mapping is fiddly — budget real time for GST + inventory allocations. Consider a wrapper lib (TallyConnector) over hand-rolled XML.
Firewall the port — no auth on it.
Roadmap: import (read) at Stage 0; voucher push (write) once invoices are stable and the master mapping is trusted — Stage 2, alongside GST (GST vouchers are where the XML earns its keep). Optional per tenant — a shop not on Tally just skips it.
