Platform Admin — Firms & Users

An operator-only area of the Metal ERP web app for setting up client firms and their login accounts. Separate dark chrome, gated on a is_platform_admin flag. Regular firm users never see any of it. Nothing here touches fleek-backend.

BUILT 2026-09-02 (uncommitted). Migration 0012, app/routers/admin.py, tools/make_platform_admin.py, 14 new tests (301 pass). Frontend src/pages/admin/ + App.tsx branch. Not yet deployed — run alembic upgrade head then python -m tools.make_platform_admin once per environment.

1 · Who gets in

  • New column app_user.is_platform_admin (bool, default false) — migration 0012.
  • Admin accounts live in one hidden “Fleek Operations” tenant — no real firm data attached to them.
  • You bootstrap yourself once per environment with a CLI:
    python -m tools.make_platform_admin --email you@fleek.com --password ••••••
  • Every /api/admin/* route sits behind require_platform_admin → 403 for anyone else.
  • /auth/me gains is_platform_admin so the SPA can route.

Routing

  • me.is_platform_admin === true → the whole app is the admin console (/admin/*).
  • A normal user who somehow hits /admin/* → redirect to /invoices.
  • No “toggle between modes” — an operator account is only an operator account.

3 · The task you described, step by step

“A client asks me to set up 3 users. I do that, then give him 2–3 usernames and passwords.”

  1. Open Operations → the firm already exists (you made it when onboarding), or click + New firm (legal name + city).
  2. In the firm’s Add user box: type ramesh@…, role owner, a password → Add user.
  3. Repeat for accounts@… and counter@… as accountant.
  4. Copy the three email/password pairs from your own notes (you typed them) and send to the client.
  5. Each user goes to the normal Metal ERP login, signs in, lands in their firm. Nothing else changes.
  6. Later: client forgets a password → you open the firm, Reset password on that row, type a new one, relay it.

4 · API surface (all behind require_platform_admin)

GET /api/admin/firms?q=  → list: name, city, flags, user_count, active_user_count
POST /api/admin/firms  {legal_name, city?} → new tenant + seed_synonyms + seed_taxonomy, NO owner
GET /api/admin/firms/{id}  → firm fields + users[]
PATCH /api/admin/firms/{id}  {legal_name?, city?, gst_enabled?, ext_inward_import?}
POST /api/admin/firms/{id}/users  {email, role, password} → global email-uniqueness check (like /register)
PATCH /api/admin/users/{id}  {role?, is_active?, password?}
DELETE /api/admin/users/{id}  soft — is_active=false

No endpoint ever returns a plaintext password — you already have it because you typed it. Argon2 hashing, exactly as /register does today.

5 · Guardrails

  • Last active owner of a firm can’t be disabled / demoted (409) — via PATCH or DELETE.
  • A platform-admin row can’t be edited through /api/admin/users/* (only the CLI touches those).
  • Email must be unique across all firms (keeps login unambiguous — same rule /register already enforces).
  • auth.login hardened: .first() + order_by(created_at) so a stray duplicate can’t 500 the login.
  • Disabled user: token stops working immediately (get_current_user already checks is_active).
  • New firm gets the same catalogue/​synonym seed a self-registered firm gets — no half-set-up tenants.
  • Roles offered: owner, accountant, viewer. Default accountant (full read/write today).
  • Desktop-first layout — this is an operator tool, not a shop-floor screen.

6 · Out of scope for this slice

  • Self-service “change my password” for firm users — you hold all credentials for now.
  • Any fleek-backend / fleek admin-UI integration — explicitly deferred.
  • Audit log of admin actions, last-login timestamps, MFA on admin accounts — later.
  • Per-firm user-management by the firm’s own owner — later, separate slice.
  • Email delivery of credentials.
