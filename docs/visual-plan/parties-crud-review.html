Parties — create, read, update, delete

First slice built on the locked shell. The current app already has a working Parties table + slide-in drawer + a complete API (GET/POST/PATCH/DELETE /api/parties, dup-name 409, PAN/GSTIN/state validation). This moves it into the list-rail + detail-pane layout, makes create happen in place, and adds the archive path for a party that documents already reference.

Search — one box, three fields

The rail search fans out: name via pg_trgm trigram similarity (typo-tolerant — "balji trdrs" still finds Balaji Traders), address (line 1 / city) and phone as exact substring (phone digits-only, so "9832" matches +919832137599). Results are ranked by name-similarity, then recency. Replaces today's plain LIKE on the name only.

How the query resolved
q = "sevok 9832"
→ name trigram similarity(legal_name, 'sevok 9832') = 0.71 (over the 0.3 floor)
→ address line1/city ILIKE '%sevok%' → also hit Rajdeep Stores
→ phone regexp_replace(phone,'\\D','','g') LIKE '%9832%' → Balaji Traders
rank = name-similarity desc, then last_txn_at desc
Search — backend
  • GIN trigram index on party.legal_name (needs pg_trgm, already enabled by 0002).
  • GET /api/parties?q= — split q; one OR of: legal_name % :q (trigram) OR similarity() > 0.3, address.line1/city ILIKE, digits-only phone LIKE. Order by similarity(legal_name,:q) DESC, last_txn_at DESC NULLS LAST.
  • Join party_address (the one default address) for the address match.
  • Response is unchanged shape — just better ranked; the rail badge (name 0.71 · phone ✓) is debug-only, off in prod.

Last seen & dormancy — data now, review UI later

Each rail row carries a last-billed line. party.last_txn_at is a real column, stamped forward-only by invoice-finalize and inward-approve. A ?dormant=true filter returns parties with no transaction inside the tenant's window (tenant.dormant_party_days, default 180). No rail chip or dashboard tile in this slice — the endpoint is built so the Dashboard can call it when it ships.

Provenance — what it is & where it comes from
  • New column party.source — manual | inward_bill | tally_import, default manual. Mirrors item.source.
  • Optional party.source_ref (the inward_bill.id) so the header can deep-link to the bill that created it.
  • Rail line: ◆ from inward bill · <bill_no> for auto-created; added manually otherwise; promoted customer → both when a customer was matched by an inward GSTIN.
  • Provenance is display-only — it never gates editing or deletion; the document_count guard does that.
  • Role filter still defaults to All, so a freshly auto-created supplier is visible without touching the filter.

Create rules — unchanged from today's API
  • Legal name required; everything else optional.
  • Duplicate name (case-insensitive, trimmed) → 409 → inline error on the name field: "A party named 'Balaji Traders' already exists" with a link to open it.
  • PAN / GSTIN uppercased on blur, format-validated client + server (422 on a bad pattern).
  • Address block is all-or-nothing — filled only if any of line1/city/state/pin is set; saved as one address, type: "both", is_default: true.
  • Created party appears in Sales / Inward party pickers immediately.

Delete vs Archive

The ⋯ menu offers whichever applies. A party with no documents → hard DELETE. A party referenced by any invoice or inward bill → Delete is disabled; Archive takes its place (hides it from pickers, keeps it for historical documents).

Unreferenced party — hard delete

Delete “Test Vendor 2”?

This party has no invoices or bills. It will be permanently removed. This can’t be undone.

DELETE /api/parties/:id → 204 · writes audit_log
Referenced party — archive instead

Can’t delete “Balaji Traders”

It’s on 12 invoices. Deleting would break those records. Archive it instead — it’ll be hidden from pickers but kept for the existing documents.

PATCH /api/parties/:id {status:"archived"} · reversible via the Archived filter

“Details pending” — advisory only

A party is complete when it has what a document needs. For M1 (non-GST) that's just legal name + one address (line 1 + city + state). Phone, email, PAN, trade name never trigger it. A name-only party — hand-typed, or later created from the invoice flow — shows details pending until an address is added. It is a hint, never a gate in M1: you can still bill an address-less customer.
