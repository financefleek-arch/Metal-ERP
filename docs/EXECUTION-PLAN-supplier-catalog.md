# EXECUTION PLAN — Supplier Catalog: import, price, barcode, customer catalog, Tally

Status: **S0 to S4 BUILT 2026-10-02 (uncommitted); S5 (promote + Tally import) next.** POC done and passed
(section 3). A feature-flagged module (`tenant.ext_supplier_catalog`) that
borrows Inward Bill Import's plumbing but has its own tables. Visual for the
workflow: `docs/visual-plan/supplier-catalog-workflow.html`.

## 1. Goal

A shop uploads a supplier's catalog PDF (photo + name + code + price per cell).
We read it into a table, the shop edits it, we give every item our own code and
barcode, the shop applies one price multiplier (with per-item override), and then
can: print a **customer catalog** with the new prices, print **barcode labels**,
and **import the chosen items into Tally** as stock items. The supplier's file is
re-sent periodically, so a later slice shows a price diff and re-prices.

## 2. Decisions

### Locked (from you)

| Decision | Choice |
|---|---|
| Columns in the review table | image, item name, item code (**auto-generated by us**), unit, price |
| Pricing | one **multiplier** for the whole catalog + **per-item override**; rounding step |
| Outputs | customer catalog (customisable at creation), barcode labels, Tally import |
| Tally scope | **chosen items only**, with bulk import |
| Tally groups | our group per item maps to a Tally stock group |
| Supplier "IN STOCK" flag | ignored |
| Catalog rows vs `Item` master | catalog rows stay in catalog tables; only **promoted** items become `Item` rows and go to Tally |
| Extraction | deterministic parser, **no LLM** for this supplier |
| Group assignment | rules, **no LLM** (87% on first pass); remainder edited in bulk |
| Group basis | **product type** (Beer Mugs, Jars & Storage, ...), one level. Brand is a parsed attribute (filter/sort), not a group. The 12-department classifier is not used for catalog groups |
| Group creation | **automatic**: a group named by the rules or by the user is created if missing; the user can rename, merge or delete afterwards |

### Decided in this plan (change cheaply if you disagree)

| Decision | Choice | Why |
|---|---|---|
| Item code format | `<prefix>-<6 digits>`, e.g. `GL-000412`; prefix chosen per catalog, default from a tenant setting; counter per (tenant, prefix), never reused | covers both "one prefix" and "one per supplier/category" |
| Barcode | Code 128 of the item code | any scanner, no registration. EAN-13 only if numeric codes are ever needed |
| Code in Tally | **Part Number only** | POC: alias-on-create fails, alias cannot equal part number |
| Unit | each item is sold **as the pack** quoted (`Nos`, 1 = one pack/set); `pack_qty` is stored and shown, not converted | per-piece pricing is out of scope for v1 |
| PDF rendering | **pymupdf** for catalog and labels (not WeasyPrint) | WeasyPrint does not load on the dev Windows box; pymupdf is already a dependency, tests run locally, barcodes are exact vectors |
| Image storage | R2 under `catalog/<tenant>/<catalog>/`, uploaded in parallel, with a local-dir fallback for dev and tests | no new infra volume or env var |
| Our group vs Tally group | a catalog item's group **is an `item_category`** (find-or-create by name, so rename/merge/delete reuse the existing category screens and promote needs no mapping); a tenant-level map sends each category to a Tally stock group; one level under a configurable root (default `Primary`) | nesting beyond that is out of scope |
| Group settings | two policies, below; defaults are `auto` and `create_missing` | see "Group settings" |

### Still open (defaults above apply until you answer)

1. Barcode on the pack only, or also on single pieces? (v1: pack only)
2. One code prefix for the shop, or per supplier/category? (v1: per catalog, default `GL`-style from tenant setting)
3. Which label sizes do you print on? (v1 presets: 50x25 mm roll, 38x25 mm roll, A4 3x8 sheet)
4. Tally side only: map our product-type groups to the pilot shop's existing Tally groups where they already have a structure (read their groups at S5); otherwise create them under the root. Our group basis is decided: product type.

### Group settings (new; none exist today)

| Setting | Where | Values | Default |
|---|---|---|---|
| `catalog_group_create_policy` | tenant | `auto` (create our group when missing) / `suggest_only` (leave blank until approved) | `auto` |
| `catalog_code_prefix` | tenant | text, 2-8 chars | derived from first catalog |
| `stock_group_root` | `tally_company` | a Tally group name | `Primary` |
| `tally_group_create_policy` | `tally_company` | `create_missing` / `existing_only` (block items whose group is not already in Tally) | `create_missing` |
| `stock_group_map` | `tally_company` | our category -> Tally group | auto-filled by name match |

Existing today: nothing for groups. The classifier already find-or-creates
`product_group` rows without a setting, and the Tally push hardcodes
`<PARENT>Primary</PARENT>`. The new settings also give the purchase push (F5-e) a
place to stop hardcoding `Primary` later.

## 3. POC evidence (2026-10-02)

Scripts and outputs: `sample data/spike-output/`. 100 items sampled evenly from
the 2,056-item Glassware Stock file, run against dev TallyPrime "Fleek".

| Step | Result |
|---|---|
| Extract | all 2,056 items parsed (172 pages) in **3.4 s**; unique codes; 2 blank filler cells skipped |
| Groups | rules classify **87.3%** of all 2,056; leftovers: casseroles, vases, margarita/ice-cream glasses |
| Catalog PDF | 100 items -> 17 pages OK. **All 2,056 -> 179 pages, 32.8 MB, 52 s** |
| Labels | 100 labels, **100/100 barcodes decode** (zxing). All 2,056: 158 s per-rect drawing, **~47 s batched** |
| Tally | **100/100 created in one envelope**, nested groups, unit, part number; read back verified |

Consequences carried into the slices:
- Image extraction must use `page.get_text("dict")` image blocks. `get_image_info()`
  is 4 s/page on this supplier's PDFs (12 min total).
- Outputs above a few hundred items cannot run inside one request (budget in S3/S4).
- The customer catalog PDF is 32 MB for 2,056 items: embed each distinct photo once.

### Tally behaviours (design constraints for S5)

- Escape `"` in attribute values or Tally rejects the **whole** request
  (`Unknown Request`). Build XML with lxml, never string concatenation.
- Nested stock groups work; blank `PARENT` = under Primary. Create on an existing
  master is an alter (unit `Nos` came back `ALTERED`), so re-push is safe.
- `<PARTNO>` is stored (Tally files it under the mailing-name list). `<PARTNUMBER>`
  is silently ignored.
- Alias on create fails `Duplicate Entry!`; an alias-only list makes the alias the
  item's *name*; `<ALIAS>` is accepted but not stored; alias cannot equal part no.
- A code is unique across names, aliases and part numbers.
- **Rejected items are kept as exception masters** ("Data > All Exceptions") that
  block the same name AND part number on retry, with only a generic
  `Duplicate Entry!`. One bad batch poisons its names and codes.
  Failures cannot be attributed per item: the response carries one `LINEERROR`
  for N exceptions.
- 115 masters imported in about 3 s.

## 4. Architecture

```
upload PDF ──> extract_grid ──> names/groups ──> codes ──> DB rows + images(R2)
                                                              │
        review UI (edit, exclude, group) <──────────────────┤
        pricing (multiplier, override, rounding) ──> sell_price
                                                              │
        ┌───────────────┬───────────────────┬─────────────────┘
   customer catalog   barcode labels     promote -> Item -> Tally push (batches)
   (pymupdf PDF)      (pymupdf PDF)       (agent, Part No., stock groups)
```

## 5. Data model

Migration `0032_supplier_catalog` (head is `0031`):

```
tenant.ext_supplier_catalog        bool default false
tenant.catalog_code_prefix         varchar(8) null      -- default prefix
tenant.catalog_group_create_policy varchar(12) default 'auto'

supplier_catalog
  id, tenant_id, supplier_party_id (null FK party), title,
  source_filename, source_sha256, source_r2_key, page_count, item_count,
  code_prefix, multiplier numeric(6,3) default 1.000, rounding_step int default 1,
  status (extracting|ready|error), error_message,
  supersedes_catalog_id (null), created_by, timestamps
  UNIQUE (tenant_id, source_sha256)                  -- same file twice = same catalog

supplier_catalog_item
  id, tenant_id, catalog_id, page_no, position,
  supplier_code, name_raw, display_name, brand, size_text,
  pack_qty int, carton_qty int,
  cost_price numeric(15,2),                          -- per pack, as quoted
  multiplier_override numeric(6,3) null,
  sell_price numeric(15,2),                          -- stored, recomputed server-side
  category_id (null FK item_category),               -- our group; auto find-or-create
  code varchar(20) not null,                         -- our code
  image_key, image_w, image_h, image_sha256,
  included bool default true,
  item_id (null FK item),                            -- set on promote
  tally_status (none|pushed|failed), tally_pushed_at,
  price_change (null|new|up|down|same|dropped),      -- S6
  UNIQUE (tenant_id, code)
  UNIQUE (catalog_id, supplier_code)
  INDEX (catalog_id, category_id), (catalog_id, included)

code_sequence    (tenant_id, prefix, next_value)  PK (tenant_id, prefix)
```

Migration `0033_catalog_outputs` (S3/S4): `customer_catalog`
(`id, tenant_id, catalog_id, version, title, options_json, item_count, pdf_key,
stale bool, created_at`) and `catalog_output_job` (`id, tenant_id, kind

- Pricing changes (S2) mark existing customer catalogs `stale`; UI offers Regenerate.
- Same sync / background-job split as S3 (about 25 items per page: 200 items
  synchronous; the 2,056-item run took 52 s).
- Tests: page count for N items, contents list matches groups, cost price never in the
  text layer (assert on extracted text), a stale flag flips on a pricing change.

### S5 — Promote and Tally import (4 days + agent release)

- **Promote** (`promote.py`): create `Item` rows (name = display name, uom `nos`,
  group -> `item_category` find-or-create, `default_rate` = sell price,
  `last_purchase_rate` = cost, `barcode`/`sku` = code, `source = catalog`); normalised-key
  dedupe: a collision **links** instead of duplicating. Selection = ids | filter | all included.
- **Preflight** `GET .../tally/preflight`: blockers = no Tally company, agent
  unreachable, item not promoted, **name or code already known** (against `Item` +
  last pull), unmapped group (not a blocker: auto-create). Offers "refresh from Tally"
  (existing pull) first. Nothing unvalidated is ever sent.
- **Group map** UI: each of our groups -> exists in Tally (matched by name against the
  last pull) / will be created under `stock_group_root` / remap. Never alter an existing
  Tally group. Stored in `tally_company.stock_group_map`, pre-filled by name match.
  Policy `create_missing` creates absent groups in the push; `existing_only` turns an
  absent group into a blocker. Both settings editable on the Tally settings screen.
- **XML** (`tally_xml.py`, lxml): `UNIT` (Nos) -> new `STOCKGROUP`s -> `STOCKITEM`
  (`NAME`, `PARENT`, `BASEUNITS`, `PARTNO`). Never an alias.
- **Push** (`tally_push.py`): new job kind `push_items`, `entity_type =
  supplier_catalog`; **batches of 50, one `TallySyncJob` per batch, sequential** (the next
  is enqueued when the previous completes OK); **stop on the first batch with
  exceptions** to limit poisoning. On exceptions: mark batch failed, show Tally's
  message plus the instruction to clear **Data > All Exceptions** before retrying, and
  block those names until the user confirms. After success, enqueue a masters pull to
  link `tally_guid` (existing mechanism). Extend `process_push_result` and the
  `tally_agent.py` result dispatch for `push_items`.
- **Agent**: add `case "push_items":` in `TallyMastersModule.cs`; `dotnet build`; cut and
  distribute a new agent build (per-environment publish step, see agent onboarding notes).
- UI: push dialog = choose -> check (blockers, group map) -> progress per batch -> result.
- Tests: XML with quotes, ampersands, 3-digit counts; envelope order; preflight blockers;
  batch sequencing and stop-on-exception; result parsing; idempotent re-push. **Live e2e**
  against dev Tally with a `ZZTEST` root group (driver kept in the repo's test tools, not
  the scratchpad).

Done when: 100 selected items land in Tally under mapped groups with part numbers, a
second push is a no-op, and a deliberately bad batch stops cleanly with a clear message.

### S6 — Re-import and price diff (2 days)

- Upload a newer catalog from the same supplier: set `supersedes_catalog_id`; join on
  `supplier_code`; set `price_change` (new / up / down / same / dropped); diff screen
  with counts and filters. **Apply** carries forward multiplier overrides, group edits,
  exclusions, promoted links and codes (a known item keeps its code); recompute prices;
  flag changed promoted `Item`s `price_review_pending`; mark customer catalogs stale.
- "Merge" mode for the supplier's small "new additions" file (adds and updates, never
  marks `dropped`).
- Tests: carry-forward of every user edit; a code is never reassigned; dropped vs merge.

## 7. Cross-cutting

- **Tenant isolation** on every query and every output; flag-off tenants get 404 on the
  whole router (same as inward).
- **Money**: Decimal end to end; no floats in pricing.
- **Deployment order**: infra limits first (S0 checklist), then API + migration, then web;
  agent build separately for S5. `alembic upgrade head` auto-runs on deploy.
- **Rollout**: flag on for the pilot firm only; S1 to S4 usable without Tally or agent.
- **Cleanup of POC residue in dev Tally "Fleek"**: group `ZZTEST Catalog` tree, `ZZTEST B3 ...`
  items, a few unprefixed probe items, and ghost exceptions (Data > All Exceptions).
- **Test data policy**: any live Tally test uses a `ZZTEST` root group and fresh code
  ranges; a failed live run poisons names and codes in that company.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Other suppliers' layouts differ | parser keys on image + price-line structure; failure path says "layout not recognised"; get 2 more supplier samples before S1 is called generic; vision fallback is backlog |
| Tally exceptions poison names | validate before send, batch of 50, stop on first failure, clear instruction in UI |
| Agent release lag for `push_items` | S1 to S4 do not depend on it; schedule the agent build when S5 starts |
| Big outputs time out | sync cap (200) + background job with polling; budgets above |
| R2 latency on 2,056 image uploads | parallel upload; fallback to bytea rows; measured in S1 |
| Pack/price semantics (price is per pack) | `pack_qty` explicit and editable; unit = the pack |
| Item master pollution | promote only on request; dedupe on normalised name; `source = catalog` |
| Customer catalog shows the supplier's branding in photos | known; masking is backlog; shown on the visual |
